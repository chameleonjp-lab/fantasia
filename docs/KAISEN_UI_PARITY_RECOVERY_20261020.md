# カイセン基準のUIへ戻すための修正計画（2026-10-20）

## 0. 結論と優先順位

**依頼内容は「ファンタジア独自のHUD最適配置」ではなく「カイセンと同じ見た目・操作・情報の整理方針を守り、ファンタジア固有の情報だけを追加する」こと。** 画面に全要素を詰めることを先に目的化しない。

この文書は方針を是正するための**計画書**であり、UI修正・検査成功・実機確認が完了した証明ではない。今回のPRでランタイムコード、公開ページ、テスト判定基準を変更しない。

優先順位は次の通り。
1. 利用者の指定（カイセンに合わせる）と既存共通UI/操作・安全表示。
2. ファンタジア固有の7陣地情報・戦闘通知の必要性。
3. 文字拡大・画面回転時の閲覧性、操作と安全表示の維持。
4. 配置探索・証拠収集など実装手段の都合。

既存 `docs/FANTASIA_SPEC.md` §0.2、§1、§2.2、§9.3／F-05／F-07 と矛盾する変更は、実装を続ける前に可視化し、必要ならユーザーに変更案を示す。

## 2. 絶対に揃える部分

| 対象 | カイセンとの一致基準 | ファンタジアで許す違い |
| --- | --- | --- |
| 上部HUD | 時計、進捗・集計、音声・一時停止ボタンの視線順、余白、角丸、半透明背景、文字階層 | 集計内容を「7陣地／残機」へ差し替える |
| 飛行計器 | 左寄りの機体HP・高度・速度・得点・弾数の表示階層とデザイン | 地上軍数、期限、ファンタジア弾数を追加 |
| 操作 | 宙返り、爆弾、射撃、速度レバー、設定したボタン位置と大きさ、44px以上の操作対象 | 魚雷など本作に存在しない武装は表示しない |
| 中央画面 | 照準の形・大きさ・基準、航空機の見え方、操作のための空間 | 地上の敵・砲台・竜・標的の意味と表示内容 |
| 右側の補助情報 | レーダーの位置・読みやすさ・共通表現 | 7陣地、竜、砲台などの独自アイコン |
| 警告・通知 | 安全通知の優先度・視認性、照準やボタンを覆わないこと | 自機狙い魔法・陣地奪還・帰還警告など内容 |
| 一時停止・設定・結果 | 共通のパネル形状・導線・操作寸法と見た目 | 陣地の詳細、残機、記録時間などのデータ |

色は原則 `#071e2b`（背景）、`#eff4ed`（文字）、`#e4c88b`（金）など既存共通指定を維持する。別テーマ・別操作ボタン・大型の新常駐パネルに置き換えない。

## 3. ファンタジア固有情報の扱い

- 7陣地の戦況は既存仕様の上端ストリップに置く。狭い縦画面では仕様にある4+3の2行構成を優先する。味方/敵/中立は色だけに頼らず意味が分かるようにする。
- 7陣地の状態、HP、残弾、期限、危険警告など既存の必要情報を**無断で削除・隠蔽しない**。ただし詳しい説明まで常時巨大表示するのではなく、重要度を整理し、停止画面などで詳細を読む既存導線を使う。二次情報の限定スクロールは既承認範囲だけ使用する。
- 操作ボタンや速度レバーの**ユーザー保存位置・サイズをCSSの画面別固定座標で上書きしない**。特に `#fire`、`#throttle`、`#pause`、`#game-sound` への一律 `!important`、固定px、保存サイズ以下への縮小を再点検する。
- 計器や警告を個別座標へ移動する方式を主設計にしない。共通HUDのまとまった領域を保ち、作品固有の情報領域を分ける。必要な調整は少数の画面寸法ルールにまとめ、重複・上書き連鎖を増やさない。
- 画面が非常に狭く200%文字で両立できない場合、数字・単位・安全警告・操作を欠落させて「成功」としない。無理な配置探索の追加を続ける前に、**比較画像と成立しない条件を示し、表示の優先順位をユーザーへ確認する**。

## 4. 段階分け（最初のPRは画面の共通部分だけ）

### P0：基準を画像と一覧で固定する（コード変更なし）
- カイセンmainとファンタジアmain、および未統合PR #20／#21候補の、同じ環境・同じモード・同じ画面サイズの「飛行中／一時停止／設定／結果」を比較。
- iPhone相当 393×852、852×393、最小条件 320×568、568×320、文字100%/200%。Normal/Easyで必要な組合せを撮影。
- 結果を「共通UIに一致」「作品固有の正当な差分」「意図しない差分」に分類。スクリーンショットを目視し、位置・大きさ・見た目・操作を確認する。自動矩形検査のみで視覚一致と判定しない。

### P1：共通HUDと操作をカイセンへ合わせる（小PR）
- `index.html`、`src/style.css`、`src/control-settings.css`、`src/control-settings.ts`、`src/input.ts`、`src/main.ts` の共通部分を比較し、見た目や操作の不要な差分を整理する。
- Kaisenの時計・集計・音/停止、HP・計器・レーダー・照準・操作ボタンの配置と階層を基準に修正する。本作のゲームルール・地上戦計算・カメラ仕様は変更しない。
- 変更前後の画像で一致を示し、基本操作・保存設定・再開の既存テストを維持する。

### P2：7陣地と警告を本作固有の追加領域へ整理する（次の小PR）
- `src/campaign-hud.ts`、`src/campaign-hud-details.ts`、`src/campaign-hud-layout.ts` とCSSの本作差分を整理。
- 7陣地を4+3等の上部ストリップへ集約し、中央の照準・レーダー・飛行計器・操作領域を侵さない。
- 経過時間/期限/敵予告/低空/圏外/復活/装填などを同時に表示するストレス状態で、欠落・重複・重なりがないことを確認。新しい巨大な常駐スクロール表示でごまかさない。

### P3：検査・目視レビュー（別PRでもよい）
- 既存の34ケース、追加50ケース、カメラ、速度レバー、15件UIなどの検査は**減らさず**正式な失敗も維持する。試験結果・画像・GitHub CI記録を省略しない。
- レイアウトの非重複だけでなく、操作ボタン中心のタッチ可能性、保存した座標・寸法の維持、照準の遮蔽、警告の判読、停止画面詳細の操作、回転後の復元も確認。
- 両作品の代表的な8画面を画像で比較し、カイセンとの差分の理由を各画面に注記。実機未検証ならそのまま明記。
- すべての見た目と操作の差分を**ユーザーがPRで判断できる状態**にする。最終承認/マージ/公開はユーザーのみ。

## 5. 現行PR #20／#21への扱い

PR #20／#21の検査記録や不具合再現は残すが、**現行の配置探索アルゴリズムを完成のために改良し続けることを新たな最優先にしない**。まずP0でカイセンとの差分を可視化し、P1/P2に必要な本体の設計を決める。

現在のPR #21は「形状を探索して配置できるか」の調査が中心であり、仕様書の最上位である「カイセンのUIと一致」の証拠ではない。検査成功は視覚的な同一性や実機体験を保証しない。既存CIの成功・失敗・未実施を区別し、合格と偽らず保存する。

**停止条件**：共通UIと異なる独自配置が増えた、保存した操作ボタン配置が上書きされた、中央の照準やレーダーが読めない、重要警告が欠落した、画面比較なしに「共通UI準拠」を宣言した場合、実装をさらに積み上げずその変更を見直す。

## 6. 受入に必要な報告形式

各段階のPR本文に少なくとも「対象SHA」「Kaisen比較画像へのリンク」「許容した本作独自差分」「意図せぬ差分の修正」「画面サイズ・文字倍率」「検査の成功/失敗/未実施」「未解決事項」「ロールバック方法」を記載。**画像のない数値検査のみをUI一致の完成判定に使わない。**

この文書に記載したステップは提案であり、製品のUI変更はまだ実装していない。
